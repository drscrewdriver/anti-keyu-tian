# 不可撤销证据：日志、修改记录、源码与生成物

> 前几篇（[framework.md](framework.md) / [provenance.md](provenance.md)）回答「现在对不对」。
> 本篇回答另一半：**「什么时候被改的、谁改的、能不能事后抹掉」。**
>
> 配套实现：`journal` / `watch-fs` / `git-audit` / `sign-checkpoint` / `verify-checkpoint`
> 实测脚本：[examples/provenance_chain_demo.py](../examples/provenance_chain_demo.py)

---

## 0. 为什么单靠文件指纹不够

指纹是**状态快照**，它有三处结构性盲区：

| 盲区 | 说明 | 本案对应 |
|---|---|---|
| 只知现在，不知过程 | 「文件是对的」和「文件曾经被改过又改回来」在指纹上完全等价 | 攻击者持续调整，团队只看到「时好时坏」 |
| 无法回答「谁」 | 指纹不含行为主体 | sudo 被谁用过，事后只能翻 shell history |
| 基线可被重拍 | 指纹由人拍，环境脏时拍出来的基线也是脏的 | 已在前篇用版本锚解决 |

所以需要三条**相互独立**的证据链。它们不互为主备 —— 任一条被绕过，另外两条仍然指认事实：

```
① 不可撤销日志    哈希链 + 签名      回答：发生过什么、顺序如何、有没有被删改
② 文件修改记录    inotify 实时事件    回答：这个文件在 T 时刻被写过（哪怕现在内容一样）
③ 源码 / 生成物   git 提交链 + 签名  回答：代码与权重是不是那份被审过的东西
```

## 1. 不可撤销日志（journal）

### 1.1 结构

每行一条 JSON（jsonl），字段：`seq / at / kind / actor / host / path / before / after / meta / prev / h / sig`

```
h_n = sha256(canonical(entry_n 去掉 h 和 sig))
prev_n = h_{n-1}
sig_n = Ed25519_sign(priv, h_n)
```

`h` 只覆盖本条内容（含 `prev`），因此**改任何一条都会改变其后所有条的 `prev`**。

### 1.2 能发现什么（全部实测）

| 攻击 | 检出码 | 原理 |
|---|---|---|
| 改某条内容 | `J-HASH-MISMATCH` | 本条 `h` 与重算值不符 |
| 改某条的 `h` 但没改下一条的 `prev` | `J-CHAIN-BROKEN` | 链断裂 |
| 删中间一条 | `J-SEQ-GAP` + `J-CHAIN-BROKEN` | seq 不连续 |
| 重排顺序 | `J-SEQ-GAP` | 同上 |
| **改内容 + 重算整条链 + 抹掉签名** | `J-UNSIGNED` | 缺失签名本身即失败 |
| 重算整条链但伪造签名 | `J-SIG-INVALID` | 无私钥签不出来 |
| 清空整个日志 | `J-TRUNCATED` | 与外部锚定记录对照 |
| 重写历史后再锚定 | 需外部锚定历史版本 | 单一锚定不够，见 §1.4 |

> **第一行之外的第六条是整个设计的关键**。实测中最初版本 `verify_journal` 写的是
> `if not sig: continue` —— 于是「重算链 + 把 sig 置空」得到一条自洽、无签名、一路绿灯的链。
> 现在默认 `require_signed=True`，缺失签名判 critical；确需无签名模式时必须显式 `--allow-unsigned`。
> **「校验存在与否」本身就是一个必须校验的维度。**

### 1.3 锚定：唯一无法在本机解决的问题

哈希链能防篡改，防不了**整段删除**。攻击者只需 `rm audit.jsonl`。

解法只有一条：把链头定期复制到**本机之外**。

```bash
fpenv journal anchor --journal audit.jsonl --out audit.anchor.json --priv key.pem
# 然后必须把 anchor 文件 + 签名推到控制面 / WORM / Git / 另一台机器
```

校验时带上锚定：

```bash
fpenv journal verify --journal audit.jsonl --anchor audit.anchor.json \
    --pub pub.pem --anchor-sig audit.anchor.json.sig
```

锚定文件本身也要签名 —— 否则改锚定文件就能掩盖截断（代码已支持 `--anchor-sig`）。

**节奏建议**：每 15 分钟或每 N 条事件锚定一次。间隔越长，被整段删除且无从发现的窗口越大。

### 1.4 锚定的局限（必须写清）

- 只保留「最新一次」锚定，无法发现「回滚到某个旧锚定再重新演进」。要防这个需要**锚定历史链**（每条锚定记录都保留并互相链接），或直接接入透明日志（Trillian / Rekor 一类）。
- 锚定本身是一次网络/人工动作，可以「忘记做」。所以它必须挂在自动化上，不能靠自觉。

### 1.5 并发写入的边界

`append_entry` 用 `O_APPEND` + 单行写入 + `fsync`，并硬性限制单条 < 4KB。这在**单写者**下安全。
多进程并发写同一 journal 时，可能读到旧的链头而写出分叉。真实部署应当：

- 每个节点写自己的 journal（`<host>.jsonl`），控制面合并；或
- 加文件锁（`fcntl.flock`）并将 journal 限制为单写者进程。

当前实现**没有加锁**，这是已知限制，不假装安全。

## 2. 文件修改记录（watch-fs）

### 2.1 它解决了什么

指纹比不出来的一件事：**「改完再还原」**。文件内容、mtime、权限全部回到原样，指纹完全干净。

实测（`provenance_chain_demo.py` 第 2 步）：

```
最终状态: mtime 还原=True  内容与原始一致
但事件流记录了 6 次写入：
  #1 fs.modify  src/model.py
  #2 fs.modify  src/model.py
  #3 fs.attrib  src/model.py
  #4 fs.modify  src/model.py
  #5 fs.modify  src/model.py
  #6 fs.attrib  src/model.py
```

**攻击者能还原文件，不能取消已发生的事件。** 这正是本案缺的那一环。

### 2.2 实现选择：为什么用 inotify 而不是 fanotify / auditd

| 方案 | 需要权限 | 记录粒度 | 实测可用 |
|---|---|---|---|
| **inotify** | 普通用户即可 | 文件级事件 + 属性变化 | ✅ 本环境 uid=1000 可用 |
| fanotify | `CAP_SYS_ADMIN`（root） | 可拦可记，含进程 PID | ❌ 未实测（需 root） |
| auditd | root + 内核审计 | 含 syscall、UID、可执行路径 | ❌ 本环境未安装 |

选 inotify 的理由：**能落地**。一个需要 root 的方案在多数训练节点上根本装不上。
代价是拿不到「谁做的」—— inotify 只给事件，不给 PID/UID。

**所以 journal 里的 `actor` 是记录者填的，不是内核给的。** 这一点必须诚实说明：
它只能证明「事件发生在该主机该时刻」，不能自证「是谁触发的」。

> 若叠加了堡垒机，这一环可以显著改善：把 `actor` 填成堡垒机会话 ID，人类操作的归因就由堡垒机负责。
> 但攻击者的多数破坏是**程序行为**（改库、改种子、杀进程），根本不经过交互登录 —— 见 §8。

要拿到主体身份，只能上 fanotify/auditd（需 root）：

```
fanotify INIT 时带 FAN_REPORT_PIDFD / FAN_REPORT_FID，事件里可取到触发进程
```
这条列为 P1，因为需要 root 与内核 ≥ 5.9。

### 2.3 覆盖范围的限制

- **递归 watch 有上限**：`max_user_watches = 524288`（本机实测）。十万级目录树要分批。
- **不监听内核变化**：inotify 是用户态接口，rootkit 可绕过。这条与 §4 的整体边界一致。
- **重启即失**：watch 是进程态，训练节点重启后必须重新挂载（用 systemd unit 常驻）。
- **事件可被合并不丢**：IN_MODIFY 可能多次，IN_CLOSE_WRITE 才代表写完。日志里两者都记，分析时以 `fs.modify` 去重。

## 3. 项目源码（git-audit）

### 3.1 思路：不重复造轮子

项目源码**已经有一份不可撤销日志**：git 的 commit 对象哈希 = 父提交 + tree + 元数据。
改任何历史都会改变其后所有哈希，且这份链条被每个协作者的克隆共同见证。

所以源码维度不该「再算一遍文件指纹」，而该**借 git 的链**，只补三件 git 默认不管的事：

| 检查 | 检出码 | 为什么 git 默认不管 |
|---|---|---|
| 工作区是否干净 | `G-DIRTY` | `git status` 要主动跑；训练机常常带一堆本地改动 |
| 未跟踪文件 | `G-UNTRACKED` | 后门常以「新文件」形式出现，而它不在任何 commit 里 |
| 历史是否被重写 | `G-HISTORY-REWRITTEN` | `--amend` / `rebase` / `force-push` 会让改动「看起来从没发生」 |
| 分支白名单 | `G-BRANCH` | 防止在 `debug-wip` 分支上跑生产训练 |

### 3.2 怎么判断「历史被重写」

只需要一个参照：**上一次审计时记录的 HEAD**。

```bash
git merge-base --is-ancestor <old_head> <new_head>
```

- 返回 0 → 新 HEAD 是旧 HEAD 的后代 = 正常演进（记 `G-ADVANCED`，info，不拦）
- 返回非 0 → 新 HEAD 不在旧 HEAD 的后代链上 = 历史被重写（critical）

实测（第 3c 步）：`git commit --amend` 后 HEAD 从 `924a37c` 变成 `d4f2567`，
`merge-base --is-ancestor` 判定非后代 → 拦下。第 3d 步的正常提交则只报 info。

**关键前提**：`expected_head` 必须存在**本机之外**（控制面/审计库），否则改本机记录即可绕过。

### 3.3 补一个能力：谁最近动过这个文件

```bash
fpenv git-audit --repo . --trace src/train.py
```

输出最近 3 次提交的作者、时间、摘要。这不是取证级别的证据（git 作者字段可伪造），
但足以回答「这个改动是谁推的」，比翻 Slack 记录快。

## 4. 生成物与已签名 checkpoint

### 4.1 签名要防的不止「文件被改」

| 攻击 | 检出码 | 做法 |
|---|---|---|
| 改内容 | `C-CONTENT` | 签名绑总 sha256 |
| 张冠李戴（A 的签名套 B） | `C-NAME-MISMATCH` + `C-SIZE-MISMATCH` | 签名绑文件名与大小 |
| 回滚冒充新进度 | `C-ROLLBACK` | 签名绑 `step`，验证时给 `--min-step` |
| 改签名文件本身 | `C-SIG-TAMPERED` | `payload_digest` 自洽性校验 |
| 无公钥时假装通过 | `C-NO-PUBKEY` | 没公钥就判 critical，不静默放行 |

实测四种攻击全部拦住，其中 `C-ROLLBACK` 最容易被忽略：
**旧 checkpoint 的签名是合法有效的**，只有 `step` 元数据能揭穿它是旧版。

### 4.2 大文件怎么办：分片流式

10GB 的 checkpoint 不能读进内存再算。实现是流式分片：

```
每 64MB 一片 → 片内 sha256 → chunks 列表
签名覆盖：总 sha256 + size + chunks_digest + meta
```

实测 200MB / 4 片：签名 0.3 秒（701 MB/s），验证同样量级。
分片的意义不只是省内存：**能定位到具体哪一片不同**，不必等整份读完。

### 4.3 最重要的约束：私钥不能在同一台机器上

代码只能检测、不能阻止这件事，所以 `sign-checkpoint` 会**显式警告**：

```
⚠ 签名主机与产物同机。若攻击者能在此机执行，就能在篡改后重新签名。
  正确做法：私钥只在控制面/离线机器，训练节点只做验证。
```

这是整套机制的**根假设**：签名方与产物方分离。做不到这一点，签名只是仪式。

### 4.4 回滚检查需要外部状态

`--min-step` 要人给。更稳的做法是控制面保存「该 trial 已接受的最大 step」，
每次验收时用其值做下限，而不是让人肉眼填。当前实现只提供 `--min-step` 参数，未接控制面。

## 5. 三条链如何配合

```
                     ┌───────────── 控制面（机器外）─────────────┐
                     │  锚定记录 / expected_head / 公钥 / 私钥    │
                     └───────┬──────────────┬──────────────┬─────┘
                             │              │              │
 ① journal  ────────────────►│  ② watch-fs ─┘  ③ git/ckpt ─┘
 哈希链+签名，每15min锚定       inotify 事件入同一 journal      提交链 + 分片签名
                             │
                     ┌───────┴────────┐
                     │  一次事故的时间线 │
                     │  T1 文件被写（事件）│
                     │  T1 内容变了（指纹）│
                     │  T2 内容还原（事件仍在）│
                     │  T3 HEAD 被 amend（git）│
                     │  T4 checkpoint 被回滚（签名+step）│
                     └────────────────┘
```

**联合查询的价值**：单独看每条链都只是「有异常」，三条合起来才能还原出「谁在什么时候做了什么」。
本案需要的正是这条时间线 —— 而不是「今天排查发现某台机器的 loss 又不对了」。

## 6. 这一切防不住什么（诚实边界）

| 攻击方式 | 为什么防不住 | 缓解 |
|---|---|---|
| root 删掉 journal 并清空锚定 | 若锚定也在本机 | 锚定必须机器外 + WORM |
| root 回滚整个日志到旧锚定 | 单一锚定无历史 | 锚定历史链 / 透明日志 |
| 内核级 rootkit 拦截 inotify | 用户态接口可被绕过 | 需 eBPF/fanotify + 内核完整性度量 |
| 私钥与产物同机 | 可篡改后重签 | **流程约束**，代码只能警告 |
| 上游包本身被投毒 | 多源全一致 | 版本白名单 + 延迟窗口 |
| 拿不到「谁做的」 | inotify 无 PID/UID | **堡垒机会话 ID（人类操作）** + fanotify（程序行为，需 root，未实测）；见 §8 |

最后一行值得单独强调：**当前实现能证明「发生过」，不能证明「是谁」**。
因为所有实现都跑在 uid=1000 下，且本环境没有 auditd。要补这一环，有两条路：

- **人的操作**：堡垒机会话录制（成本最低，且顺带解决了入口收敛）
- **程序的行为**：fanotify / auditd（需 root，能拿到触发进程的 PID/UID）

注意这两条**只覆盖各自一半**。攻击者改 PyTorch 源码用的是落在共享盘上的脚本、由训练进程加载执行，
那属于程序行为 —— 堡垒机录不到。所以 §8 的结论是「分工」而不是「替代」。

## 7. 落地顺序

1. **本周**：`journal` + 每小时 `anchor` 推到 Git（成本最低，覆盖「改动被记录」）
2. **本周**：`git-audit --expected-head` 接进 CI，把 HEAD 记到控制面
3. **下周**：`sign-checkpoint`，私钥放控制面，训练节点只验
4. **下周**：`watch-fs` 常驻（systemd unit），只监听关键目录（框架库、启动脚本、配置）
5. **若规划堡垒机**：先落实 §8.4 三个前提（网络强制 + 录制异地 + 账号映射），
   再砍掉「节点登录记录审计」与「未授权登录外扫」；`authorized_keys` 基线保留
6. **后续**：fanotify 取 PID/UID（需 root）；锚定接透明日志

## 8. 叠加堡垒机之后：哪些可以砍、哪些反而必须加

堡垒机（跳板机 / jump host）解决的是**「谁、从哪、登进来了」**，
本文四层解决的是**「文件现在对不对、曾经被谁动过、产物是不是原件」**。
两者不重叠的部分，才是判断能不能砍的依据。

### 8.1 一句话结论

**堡垒机换掉的是「身份」，不是「完整性」。** 四层里只有一层被真正替代，其余照旧。

### 8.2 可以砍 / 降级的

| 原措施 | 堡垒机之后 | 理由 |
|---|---|---|
| journal 的 `actor` 字段（记录者自填） | **升级为堡垒机会话 ID** | 这是本文最弱的一环，堡垒机直接补上（见 §2.2） |
| 节点登录记录审计（谁登了这台机） | 砍掉，改读堡垒机会话日志 | 登录入口收敛后，节点本地登录记录本就该为空 |
| 每日「未授权登录」外扫 | 砍掉，改由堡垒机告警 | 同上；但见 §8.4 的前提 |
| `access-control` 作用域里的 `/etc/ssh` 巡检频次 | 每小时 → 每日 | 登录入口收敛后，改动频率下降；**但不能停**，见 §8.4 |
| `journal` 每条都强制记 actor 的要求 | 放宽 | 人类操作的归因交给堡垒机，本地只记「发生了什么」 |

### 8.3 不能砍的（堡垒机完全不管这些）

| 措施 | 为什么堡垒机替代不了 |
|---|---|
| 文件指纹 / `audit` | 堡垒机不校验文件内容。它只保证「你从哪进来」，不管「进来的文件对不对」 |
| `watch-fs` 事件链 | **训练进程、CI 下发、调度器、容器内操作全都不经过堡垒机**。本案攻击者大部分动作是程序行为，不是交互登录 |
| `git-audit` | 代码是通过 push 进来的，不走堡垒机终端 |
| checkpoint 签名 | 产物是程序写的，堡垒机看不见 |
| 供应链 / 多源核对 | 包从镜像站拉，与堡垒机无关 |
| **私钥不在节点** | 堡垒机不改变「谁能签」这件事 |
| **`~/.ssh/authorized_keys` 基线** | 见 §8.4，这是最关键的一条 |

### 8.4 堡垒机的三个致命前提（不满足则整层失效）

**① 网络层必须强制「节点只接受堡垒机来源」**

如果节点仍能直连 SSH，堡垒机只是「多一个可选入口」。攻击者（或有权限的人）直连节点、
往 `authorized_keys` 加一行、做完全部动作、再删掉，堡垒机日志里**什么都没有**。

所以：安全组 / 网络策略 / `sshd_config` 的 `AllowUsers` + `ListenAddress` 必须写死为堡垒机网段。
**这条不落实，`authorized_keys` 巡检绝不能砍** —— 它是唯一的兜底。

**② 会话录制不可关闭，且必须实时异地**

本地录制的会话日志，攻击者有 root 就能先停录制再动手。要求：
- 录制代理以独立账号运行，节点管理员无权停
- 录制流**实时**（不是会话结束才落盘）转发到异地
- 堡垒机自己也有审计日志，且该日志进同一套 journal

**③ 堡垒机账号 ≠ 节点账号，映射必须固定**

堡垒机登录后如果允许任意 `su` / 提权到任意节点账号，「谁做的」又回到猜。
要求：堡垒机上的身份到节点上的账号是一对一映射，且该映射本身纳入变更审批。

### 8.5 真正的收益：取证从「猜」变成「二分」

这是加堡垒机最被低估的价值。

节点上任何一次改动，只可能来自两条路径：

```
① 有人登录后操作  → 堡垒机会话录制里有            （需要 §8.4 的三个前提）
② 程序自己跑的    → inotify 事件链里有

两条都有记录 ⇒ 不存在「查不到来源」的第三态
```

以前的做法是在一堆日志里捞、猜「是不是某个人干的」。现在只要问两个问题：
**这个时间点有没有堡垒机会话？事件链里有没有对应写入？** 两个都否，才需要怀疑更深的东西（rootkit）。

攻击者要绕过，必须同时伪造两套记录，且其中一套在异地 —— 成本高到不值得。

### 8.6 堡垒机自己成了新的单点

| 新风险 | 缓解 |
|---|---|
| 堡垒机账号被接管 = 全部节点 | 强 MFA + 堡垒机本身的登录进 journal + 高危命令双人审批 |
| 堡垒机运维人员成为新内鬼 | 堡垒机管理员与训练集群管理员**不得是同一人** |
| 会话录制可被关闭 | §8.4 ② |
| 堡垒机到节点的密钥泄露 | 该密钥定期轮换；密钥使用本身记入 journal |

**堡垒机的管理员必须是这套审计的"被审计对象"之一**，否则只是把风险从节点搬到了堡垒机。

### 8.7 一个反直觉的结论

叠加堡垒机**不会**让本文的四层变少，只会让它们**分工更清楚**：

- 堡垒机负责**人**这条线（谁进来、做了什么交互操作）
- 指纹 + 事件链负责**程序**这条线（文件变成什么、什么时候被写）
- git + checkpoint 负责**产物**这条线（代码与权重是不是原件）

这三条线在架构上是正交的。试图用堡垒机替代其中任何一条，都会在「程序行为」这个最大盲区上失守 ——
而本案攻击者的破坏手段，绝大多数正是程序行为。
