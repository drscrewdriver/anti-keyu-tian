# 为什么一个 SRE 不该随便给出 root 密码

> 这一篇不讲机制，讲判断。
> 前面几篇（[framework.md](framework.md) / [provenance.md](provenance.md) / [audit-chain.md](audit-chain.md)）说的是「怎么建」。
> 这篇说的是「为什么值得建」——以及不建的话，账记在谁头上。

---

## 0. 给出 root 密码时，你同时给出的另一样东西

大多数人把「给 root 密码」理解成一次权限授予。它有更麻烦的隐性条款：

**你把「出事后能不能查清」这个能力，一起给出去了。**

一旦同一个口令被三个人知道，那台机器上发生的一切就再也无法归因。日志里全是 `root`，
`sudo` 记录指向一个共享账号，`authorized_keys` 谁都能加。半年后某次训练结果异常，
你能确认的只有「有人用 root 干过」，不能确认是谁、也不能排除是自己团队的人误操作。

这时候所谓的「信任」，其实已经变成了**「放弃追查」**。

我见过的最常见辩解是：「都是自己人，给了方便。」这句话在没出事时听起来完全成立。
它的问题不在逻辑，在于**它把一笔未来才兑付的账，记成了当下的零成本**。

---

## 1. 信任成本债：本金、利息、复利

「信任成本债」这个词是我自己用的，但它对应的东西很具体：

| | 内容 |
|---|---|
| **本金** | 一次违约造成的实际损失（算力、返工、事故处置） |
| **利息** | 违约之后，**每一次需要证明清白的成本** |
| **复利** | 机制没建立时，人事一变动，这笔债重新欠一遍 |

本金是最好算的，也是最容易被误认为「全部成本」的部分。真正压垮团队的是利息和复利。

**利息长什么样**：出过事后，团队开始要求一切操作留痕、要求双人复核、要求变更审批。
这些流程本身是对的，但它们是在**用流程弥补归因能力的缺失**——成本高、体验差、还会被绕过。
更糟的是它作用于所有人：一个人的违约，让所有人多背一套流程。

**复利长什么样**：机制是组织的记忆，人是会流动的。老 SRE 记得「那台机器不能给 root」，
他离职了，这条记忆就没了。新来的人重新欠一遍。所以你会看到同一类事故在不同团队反复发生——
不是因为大家蠢，是因为**每个组织都在用自己的学费重新买同一个教训**。

---

## 2. 本案的真实账本

田柯宇案的公开陈述里，被反复提到的不是钱，是这个：

> 分布在北京、上海和西雅图的中美团队轮流值守，24 小时监控训练程序的运行情况。团队每天早晚召开会议，交接排查工作……
> 反复的失败不仅消耗了团队的时间和精力，也逐渐让人开始怀疑自己的技术判断，甚至怀疑这些排查工作究竟还有没有意义。
>
> —— [keyu-tian-sabotage.github.io](https://keyu-tian-sabotage.github.io)

注意最后半句。**被摧毁的不只是时间，是技术判断本身。**

一个工程师最值钱的能力是「我相信自己的排查结论」。当一个人连续两个月追查一个永远抓不到的 bug，
他会开始不相信自己。这种损伤不会写在事故报告里，也不会出现在赔偿金额里，但它真实存在，
而且恢复期远超故障本身。

再叠加一层：攻击者**在同一个群里，参加同一次排查会**。这不是技术问题，
这是把一个团队赖以协作的前提（同事不会害我）直接拿去当了攻击面。

所以这笔账不能只算成「800 万索赔 / 50 万判决」。那只是法律层面的定价，
和团队实际付出的东西不是同一个量纲。

## 3. 翻转：审计是给诚实的人准备的

这是我最想让做运维的人记住的一件事。

通常大家把审计理解成「防着人」。所以引入审计时会有人不舒服，觉得不被信任。
这个感受是真实的，但它来自一个错误的前提：**以为审计是用来抓坏人的**。

审计真正服务的是好人：

- **有记录，好人才能被证明清白。** 没有记录，出事时所有人都在嫌疑名单上，包括你。
- **有机制，好人不需要靠人品担保。** 你不需要同事「相信我」，你需要的是「这件事本来就不需要谁相信我」。
- **有边界，好人不必做那个拒绝的人。** 「不给 root 密码」如果是制度，你就不用当那个扫兴的人；
  如果是你的个人坚持，你就是团队里那个难搞的家伙。

最后这条尤其重要。**制度存在的意义之一，是把「得罪人」这件事从个人身上拿走。**

一个 SRE 最难的不是技术判断，是在「同事开口要权限」的场合说不了「不」。
如果这个「不」写在制度里，他就不必用自己的关系去付这笔成本。

## 4. 人格化信任 vs 制度化信任

| | 人格化信任 | 制度化信任 |
|---|---|---|
| 载体 | 「我信老张这个人」 | 「这件事有记录，谁做都一样」 |
| 人事变动 | 归零 | 不受影响 |
| 出了事 | 关系破裂 + 无法归因 | 查得清，该谁的责任是谁的 |
| 成本 | 平时为零，一次性兑付 | 平时有固定成本，事故时成本可控 |
| 对好人的保护 | 弱（要一直证明自己值得信） | 强（不需要证明） |

**人格化信任不是错的，它是不够的。** 它在小团队、短周期里极其高效，
但它的失效模式是断崖式的：一旦违约，全部信任一次性归零，而且无法局部修复。

制度化信任的失效模式是渐进的：某个环节出问题，修那个环节，其余照常。
这就是为什么成熟组织看起来「流程繁琐」——它们不是在防人，是在**把信任做成可维修的东西**。

## 5. 可数与不可数

停训一次的成本是**可数**的：几十分钟到几小时卡时，一个明确的数字。

带毒训练一次的成本是**不可数**的：几周后才发现，而且你无法确定哪些实验受影响、
哪些模型已经上线、哪些结论要推翻。不可数的成本，在预算会上永远赢不了可数的成本——
这也是为什么安全投入总是排在「优化训练速度」后面。

但还有一类成本比这更不可数：**一个团队不再相信自己的排查结论。**

所以判断标准不该是「这套机制要花多少人力」，而该是：
**「我愿意用多少可数的成本，去买掉一次不可数的兑付？」**

前几篇里那些机制的价钱是清楚的：基线拍拓 10941 个文件 0.5 秒，200MB checkpoint 签名 0.3 秒，
journal 只写一行 JSON。这些几乎是零成本的。真正贵的从来不是技术，是**有人肯把这件事当成规程写下来、
并且每天都执行**。

---

## 6. 所以具体做什么

不是什么宏大工程，是几件可以今天就定的事：

1. **root 密码不给个人。** 要特权操作，走工单 + 堡垒机，事后能查到是哪次会话。
2. **共享账号禁止用于变更。** 谁做谁登录自己的账号，这是归因的最低前提。
3. **审计日志必须异地。** 本机日志可被 root 删除，等于没有。
4. **制度性地拒绝。** 把「不给 root」写进入职须知，而不是靠每个 SRE 临场硬扛。
5. **承认这是债。** 不建机制的每一天，都在给未来记一笔没有明细的账。

这五条里没有一条需要新技术。它们需要的是**有人愿意当那个把话说清楚的人**。

---

## 结语

技术防护解决「能不能改」，审计解决「改没改、谁改的」。
但这两件事真正要保护的东西，是团队里那句没人说出口的话：

**「我相信自己的判断。」**

这句话一旦碎了，补起来比任何系统都难。
