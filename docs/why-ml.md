# 为什么 ML 平台特别值得被防护

> 上一篇 [why.md](why.md) 讲的是「为什么任何系统都该有审计」。
> 这一篇讲的是更具体的判断：**为什么 ML 平台在这件事上的暴露程度，显著高于普通服务**。
>
> 如果这个判断不成立，后面那堆机制就是过度设计。

---

## 0. 一句话结论

ML 平台同时具备两个罕见属性：**破坏的杠杆比极高**，**错误的可见性极低**。

单看任何一条都不算特别 —— 高杠杆的东西很多（数据库、支付），可见性低的也有很多（嵌入式、批处理）。
但两者叠加，且**系统的正常噪声本身就足以掩护攻击**，这个组合在 IT 里相当少见。

下面九条，是这套机制「长成这样」的原因。设计不是凭空的，是这些性质倒逼出来的。

---

## 1. 错误是沉默的

Web 服务出错会立刻可见：500、超时、错误率飙升、用户投诉。它有天然的**负反馈**。

训练出错不会。它表现为：

- loss 曲线还在往下走，只是比预期慢
- 指标差一点，但不至于报警
- 某个 rank 偶尔异常，重启又好了

**没有任何一条会触发告警。** 你只有两个发现途径：跟预期对比（需要基线），或者事后复盘（已经晚了）。

这类错误在可靠性工程里有个说法：**silent failure**。而 ML 训练是天然容易产生 silent failure 的
系统 —— 因为「跑完了」和「跑对了」在日志上长得一模一样。

---

## 2. 攻击者藏在噪声里（最深的一条）

这是 ML 平台真正的特殊性所在。

大规模训练本来就是不稳定的。同一份代码：

- 硬件有静默错误（SDE），浮点结果偶发偏差
- fp8/bf16 混合精度、异步通信、非确定性归约，导致每次跑结果都略有不同
- 集群调度抖动、NCCL 超时、显存碎片

也就是说，**「有时正常、有时异常、无法复现」本来就是分布式训练的常态**。

于是攻击者不需要制造「异常」，他只需要**把自己的行为伪装成已知的异常类型**：

| 真实故障 | 攻击伪装 | 表面现象 |
|---|---|---|
| 硬件 SDE | 改种子 | 偶发数值偏差 |
| NCCL 超时 | 按 rank 跳过集合通信（`2⁻¹⁸` 概率） | 训练卡死 |
| OOM kill | `pkill torchrun` | 进程退出 |
| 数据管线 bug | `manual_seed(time.time_ns())` | 样本顺序不一致 |

本案团队排查了五个月，反复陷入「定位到 → 重启就正常 → 规律失效」。不是他们能力不够，
是**这套系统本身的噪声水平，足够容纳一个刻意藏身的攻击者**。

推论：在 ML 平台，「异常检测」这条路先天不可靠 —— 你无法从现象区分故障与攻击。
唯一可行的方向是**证明「不该变的东西没变」**，而不是「抓出异常的东西」。这也是本仓库整套机制的出发点。

---

## 3. 没有 reference output，所以无法对拍

判断一个系统对不对，最有效的方法是拿同输入的已知正确输出去比。Web 服务有回归测试，
编译产物有字节级对比，数据库有一致性校验。

训练没有。它有三个不可逆的性质：

- **随机性**：同样的 seed 在不同硬件/驱动/并行度下结果不同
- **代价**：验证一次要重训一次，几千卡时起步
- **无金标准**：模型「好不好」本身就是主观的 eval 指标

所以 ML 平台无法用「重跑一遍对比」来验证完整性。**必须靠外部记录**——
记下当时是什么、由谁定的、之后有没有变。这直接推导出基线、版本锚、签名，以及日志链。

---

## 4. 破坏的成本极低，效果极大

本案最刺眼的一行代码：

```python
maximize = group["maximize"] = True
```

一个字符串的改动，让优化器朝反方向走。代价：数千卡、五个月排查。

对比一下其他系统：要让一个 Web 服务持续数月返回错误结果且不被发现，你需要改业务逻辑、
绕过测试、躲过监控 —— 攻击面大得多。而训练系统里，**改一个默认值就够了**，
因为没有任何东西会因此报错。

杠杆比 = (破坏效果) / (破坏成本)。ML 平台在这个比值上几乎是极值。

这也解释为什么「内部人」在这里格外危险：他不需要高深手段，只需要知道改哪里。

---

## 5. 资产密度：一台机器就是一笔钱

普通业务服务器出错，损失的单位是「请求」「用户」「分钟」。
训练节点的单位是 **GPU 小时**，可以直接乘单价换成钱。

- 一个 8×H100 节点，按市场价约每小时数百元
- 千卡集群跑一周 = 一笔七位数的支出
- 而一次「带毒训练」的浪费，是整个窗口，不是几分钟

**这在安全预算上反而是好消息**：ML 平台的安全 ROI 比大多数领域更容易算清。
停训一小时的损失是可数的，带毒跑一周的损失也是可数的，两者相减就是这套机制的价值上限。
不需要用「万一出事」来说服人。

（呼应 [why.md §5](why.md)：可数成本与不可数成本的区别。ML 平台的妙处是它两头都能量化。）

---

## 6. 信任边界天然模糊

普通服务通常有清晰的边界：DMZ、内网、数据库层。而训练集群的协作方式本身就要求打破边界：

- **共享存储**：同组可写，为了方便共享数据和避免重复劳动（这是本案的根因之一）
- **多团队共用集群**：资源竞争时，改别人实验的动机是真实存在的
- **人员流动大**：实习生、外包、跨部门协作，权限回收往往滞后
- **长任务**：一个跑三周的任务，人员可能中途换了

这些不是管理疏忽，是**大规模协作的必要条件**。你很难一边要求高效共享，一边维持严格的权限隔离。

所以 ML 平台的防护不能靠「收紧权限」单点解决（那会直接损害协作效率），
必须接受「有人能改」这个前提，转而保证**改了必然留痕**。

---

## 7. 供应链是「活的」

编译型项目在编译期确定依赖。Python 训练环境的依赖在**每次运行时**都可能变：

- `pip install` 拉的是当时的 latest
- 镜像是可以事后被改的（同 tag 重新 push）
- 依赖树深度大，任一环被投毒都难以发现

本案攻击者改的是**已安装的 PyTorch 源码**——不是项目代码，也不是依赖声明。
这意味着 `requirements.txt`、`pip freeze`、代码 review **全部看不见**。

ML 生态对「即时安装」的高度依赖，让「运行时的文件状态」成为一个必须单独校验的对象。
这是 [framework.md](framework.md) 把 `site-packages` 列为最高优先级作用域的原因。

---

## 8. 成果验收依赖「相信报告者」

传统工程里，代码可以被 review。模型训练成果不能 —— 你无法 review 一次训练。

Leader 判断下属进展，实际上依赖三件事：周报里写的数字、demo 跑出来的效果、以及**对这个人的信任**。

本案的 VAR 事件正是打在这里：把开源模型 PixArt 的输出包装成自己训练的成果，
在 inference pipeline 里给所有 prompt 加 `City` 前缀以避免被同 prompt 对比识破，
再把整个 pipeline 打成二进制交给同事部署 —— 部署的人无法检查内部实现。

这不是单纯的安全问题，它说明一件事：**当验证成本高于信任成本时，组织会自动选择信任。**
而攻击者知道这一点。

技术上能做的只有一件：把「产物」和「声明」绑定起来。签名 checkpoint、可复现的 eval、
训练日志与权重哈希对拍 —— 让「我说的」和「实际的」可被第三方独立验证。

---

## 9. 时间放大效应

训练是长期任务。一个三周的训练，第二天被注入，后面十九天的算力全废；
但你很可能第二十天才能确认。

而且**污染是继承的**：从被污染的 checkpoint 继续训练，错误会被继承下去。
所以 checkpoint 不只是「进度」，它是**病毒载体** —— 本案里它还被用作命令后门的载体。

这解释了为什么 `sign-checkpoint` 要绑 `step` 并检查单调性：
回滚到一个「干净但过时」的 checkpoint，是一种几乎不留痕迹的攻击。

---

## 10. 那么，什么样的 ML 平台不需要这些

诚实地说边界。以下场景，这套机制属于过度设计：

- **单机、单卡、几天内跑完**的实验：重跑成本低于建机制的成本
- **纯离线研究**，没有共享存储、没有多团队、没有外部人员
- **结果不进入生产**，只用于论文或内部探索
- **没有 GPU 成本压力**（比如用免费额度）

判断标准很简单：**问「如果这次训练结果不可信，我损失多少」。**
如果答案是「重跑一次」，不需要这套东西。如果答案是「三周算力 + 一个已上线的模型 + 团队两个月的判断力」，
那它值得。

---

## 11. 这些性质对应哪些机制

| ML 平台的性质 | 倒逼出的机制 |
|---|---|
| 错误沉默、无法对拍 | 基线拍拓 + `audit` 门禁（比对参考基线） |
| 攻击藏在噪声里 | 不做异常检测，改做「不该变的有没有变」 |
| 无 reference output | 用 ctime / inode / 签名等**外部证据**替代输出比对 |
| 停训代价高 | 检测放在启动前，不让脏环境烧卡 |
| 无人能独立验证 | 版本锚 + 来源核对 + 签名 checkpoint |
| 供应链是活的 | `site-packages` 逐字节哈希，`F-LOCK-DRIFT` 查版本漂移 |
| 改完可还原 | journal 事件链 + 外部锚定 |
| 长任务、状态继承 | checkpoint 分片签名 + step 单调性 |
| 内部人、协作必要 | 不追求「改不了」，追求「改了必然留痕」 |

**最后一条是整套设计的取舍原则**：ML 平台无法做到 tamper-proof（协作要求开放性），
所以退一步做到 tamper-evident（改动必然留痕）。这是现实约束下的最优解，不是妥协。

---

## 结语

普通系统的安全，多数时候在防「别人拿走我的东西」。
ML 平台的威胁，主要在防「别人让我的东西看起来是对的」。

前者损失的是机密，后果明确；后者损失的是**判断力**，后果是延迟几周、跨越多人的误判。

这也是为什么本案真正的代价，不是那 800 万索赔，而是原文里那句：

> 「反复的失败……逐渐让人开始怀疑自己的技术判断，甚至怀疑这些排查工作究竟还有没有意义。」

一个平台的防护做得好不好，最终看的是：**在这台机器上做事的人，还相不相信自己的结论。**
